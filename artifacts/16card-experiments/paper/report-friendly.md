# H20×16：网络慢时，怎样减少训练等待

逐步学习入口：[训练系统篇](../../一步步认识训练系统实验-friendly.md)。本报告保留完整设置和查证数字。

本报告解释截至 2026-10-21 的实测。原始设置、逐次表格和文献保留在[技术报告](report.md)；2026-10-25 的取消状态见[终态说明](../cancellation-20261025-friendly.md)。

实验最明确的结果是：两台 H20 各 8 卡训练同一模型时，把高频参数分片通信留在机内，能减轻普通 Socket 网络的开销。这是并行布局的结果。它还没有证明混合 H20 / 910B4 比最佳同构更快，也没有证明改变同步频率后达到同一质量更快。

## 先理解这张图

![H20 16 卡的网络与分片布局实测](../../figures/h20-training-friendly.png)

柱为两次均值，黑点为两次实际计时，不是置信区间。橙色斜纹方案改变训练规则，不能直接当成与同步训练等质量的比较。三个面板共用秒轴；不同模型 batch 和 token 量不同，不能跨面板直接比较硬件效率。

FSDP 把参数和优化器状态分散到不同卡，计算某层时再收集需要的参数。若在全部 16 卡间分片，这种通信会频繁跨机器。HSDP 则在每台 8 卡内分片，两台之间保存对应副本；参数物化留在机内，但仍跨机器同步梯度。

RDMA 与 Socket 是本次 NCCL 的两种实际网络路径。RDMA 不是“申请了多台机器就自动成立”，本次由通道日志确认。CPU/TCP 参数平均是另外一种算法路径，包含设备搬运和主机聚合，不能与强制 Socket 的 NCCL 路径混称。

## 同样 16 个更新，测了哪些差别

每个配置重载初始权重，运行 16 个更新，重复两次。三模型各七配置，共 42 次训练计时。耗时取全部 16 个 rank 的最慢墙钟，含数据准备、更新、日志、末端等待和最终交换，排除模型加载与资源排队。

| 方案：两次均值，秒 | 3.5-4B | 3.5-9B | 3.8-27B |
|---|---:|---:|---:|
| 全局 FSDP16 / RDMA | 30.03 | 36.31 | 70.56 |
| 全局 FSDP16 / Socket | 109.56 | 211.34 | 660.09 |
| 机内分片 HSDP 2×8 / RDMA | 31.62 | 33.19 | 60.79 |
| 机内分片 HSDP 2×8 / Socket | 48.29 | 83.45 | 216.60 |
| CPU/TCP 每步梯度同步 | 90.80 | 158.22 | 467.36 |
| CPU/TCP 每 4 步参数平均 | 43.38 | 61.92 | 165.02 |
| CPU/TCP 每 16 步参数平均 | 31.74 | 37.48 | 83.30 |

全局分片换为 Socket 后，三个模型平均耗时分别为 RDMA 的 3.65、5.82、9.36 倍。这反映本次短序列工作负载中的网络敏感性，不能线性外推到其他集群或长上下文。

在 Socket 下改为 HSDP，耗时分别减少约 55.9%、60.5%、67.2%。这个对照保持同步优化器语义，说明不用改变为低频局部训练，布局本身就可以改善执行时间。只有两次观测，表中差距不能当成跨日期、跨节点的稳定置信结论。

## 每 16 步平均参数，为什么还要保留限制

设第 \(j\) 组本地模型为 \(\theta_j\)。参数平均得到 \(\bar\theta=(\theta_1+\theta_2)/2\)。两组在平均前分别做 AdamW 更新，并保留各自的 Adam 状态。一般情况下，这不等于按全局 batch 每步同步梯度的 AdamW。

本次 16 步实验中，H=16 只在末尾交换一次。27B 的 83.30 秒说明这种短程路径减少了通信等待，但尚无长期质量曲线、多个 seed 或固定质量门槛时间。不能把它和 660.09 秒的比值称为等质量训练加速。

本实现没有 DiLoCo 的外部 Nesterov 优化器，因此称参数平均 / Local SGD，不称完整 DiLoCo。[DiLoCo 原论文](https://arxiv.org/abs/2311.08105)用于背景比较。

## 理解实验所需的设置

| 模型 | 实际文本主干参数 | 层数；DeltaNet / 完整注意力 | 全局 batch | 每 case 监督 token |
|---|---:|---|---:|---:|
| Qwen3.5-4B | 4,205,751,296 | 32；24 / 8 | 32 | 65,151 |
| Qwen3.5-9B | 8,953,803,264 | 32；24 / 8 | 32 | 65,151 |
| Qwen3.8-27B | 26,895,998,464 | 64；48 / 16 | 16 | 33,149 |

仅训练文本主干，不包括视觉编码器或 MTP。参数数由配置构建 meta 模型计数；9B / 27B 文件哈希已与官方清单核对。3.8 沿用 3.5 架构基础，版本更新不能当成全新主干。

数据为 GSM8K 公开训练源，序列最多 512 token、监督答案最多 256 token。共同实现采用 Transformers 5.2、SDPA、FSDP2，FP32 master / AdamW、BF16 计算、FP32 梯度归约；CUDA Torch 2.9.1。没有生产连续批处理或专用 FLA kernel，所以是共同实现的性能，不是硬件最优值。

27B 初始化先在 CPU 加载 BF16，再逐层转 FP32 并分片，避免完整 FP32 权重先落在单卡。聊天文本的 prompt 前缀并不保证独立分词后仍是 token 前缀，训练按文本边界拆分后分别分词，保持生成 prompt 契约。

3.8 使用 Transformers 的 Qwen3.5 兼容实现，正式质量结论还需与官方参考做输出 / 梯度一致性校验；文件和参数覆盖通过不能代替这种验证。

## 生成与更新分工，测到的是发布成本

另一组九个 case 把两台 H20 分为 8 卡生成、8 卡训练，每 case 16 个更新。训练用实际生成答案做交叉熵 CE，发布间隔为 4 / 16，另测固定教师。每配置只有一次观测。

| 模型 | 每 4 步发布，秒 | 每 16 步发布，秒 | 固定教师，秒 |
|---|---:|---:|---:|
| 3.5-4B | 209.41 | 97.48 | 66.14 |
| 3.5-9B | 363.98 | 135.20 | 67.50 |
| 3.8-27B | 915.92 | 321.87 | 130.87 |

最终 BF16 发布计入时间。27B 每次文本参数约 53.79 GB，9B 约 17.91 GB，4B 约 8.41 GB。发布还包含 CPU 参数物化、哈希、发送和加载，不能全部解释成网络耗时。

固定教师不接收新权重，适合离线蒸馏产数等工作，却改变了生成行为。这里没有 reward、KL 约束或 importance correction，不是 PPO / GRPO，也不能用 CE 下降证明 RL 效果。

## 异构比较完成到哪里

历史 4＋4 的 Qwen3.5-4B 八更新测试中，逐步同步为 101.63 秒，每 8 步参数平均为 24.58 秒；H20×8 和 NPU×8 分别 19.20、18.70 秒。较好混合生成 / 更新方向为 44.24 秒，NPU 同构分工 40.70 秒。早期实验没有证明混合胜过更快同构。其数据量和计时范围不同，不能直接接到本报告 16 卡表中。

早期 8＋8 的 Qwen2.5 已有完成事件和部分计时：逐步同步两次 170.10 / 200.35 秒，H4 为 59.51 / 93.04，H16 为 33.17 / 54.92；后半程新架构详细计时没有全部导出，不能由“完成”补出数字。

新版 H20×16 已完成；新版 NPU×16 和混合 8＋8 在原报告截止时仍未分配 worker，10 月 25 日确认取消。原技术报告“继续完成两组”的建议是当时建议，当前没有继续排队。完整三组比较仍缺失。

现有结果支持先优化同构布局，再讨论异构组合。若以后重新研究收益，需比较调优后的 H20 同构、NPU 同构和混合组，保持模型、global batch、训练规则一致，并补齐质量门槛曲线；单纯更少通信不能代替模型质量或费用证据。
