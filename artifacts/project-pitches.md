# 训练 Infra 项目的几种表述

当前阶段：方案设计与通信可行性验证；独立 H20/910B4 TCP、CPU Gloo 及设备写回已通过。完整训练与恢复尚未实施，面试成果版仍是模板，使用时必须替换为实际完成的工作与证据。

最新决策：原“双副本训练、周期平均”方向不直接扩成 16 卡项目；固定 8＋8 胜过两种同构 16 卡尚无直接证据。优先评估有真实阶段互补性的 RL 分工，见 [文献与立项判断](heterogeneous-training-decision.md)。以下为原候选方案的历史表述。

## 先明确项目的价值

原方案包含 FSDP、混合精度、DiLoCo、算子融合、数据处理和评测，范围较宽。大部分能力已有成熟实现，把它们配置起来训练一个模型可以证明工程实践，但不足以证明核心训练 Infra 能力。

推荐把主贡献收敛为：**实现并验证 H20 与昇腾训练进程之间的模型更新同步和故障恢复，使不同硬件上的模型副本在低带宽连接下能参与同一轮训练。**

每组机器内部沿用已有分片训练框架，组间交换模型更新。第一版固定成员并阻塞同步，先解决状态一致性；后续才研究慢节点、掉线后继续训练和动态成员。同步频率改变会影响优化过程，因此始终以调优同步基线的质量与训练时间作对照。

这是候选工程切入点，不是已经证实的技术空白。torchft、prime-diloco 已有相关同步和恢复能力；需要先验证哪些组件能直接复用，哪些在选定 NPU 环境中确实需要新增支持。

通信可行性已在本次 HL 两个不同节点上实测：H20/NPU 设备张量经 CPU 中转后，TCP 与 Gloo 聚合写回均通过。标准 NCCL/HCCL 不提供设备混合 collective；仅共享存储可达时要改成文件交换协议。实测范围见 [通信报告](communication-results/report.md)。下面各版本仍描述完整训练与恢复的拟实现目标。

## 1. 简洁版

做一个训练系统，让 H20 和昇腾分别训练同一个决策模型，再通过较慢的网络定期交换更新。重点是让模型更新传输和故障恢复保持一致：一台机器在传输中途退出后，系统能够识别这轮训练是否完成，并从完整状态恢复。最终用真实 8B–32B 训练任务证明，在模型质量接近的条件下，这种方式是否比每一步都等待全体机器同步更快。

## 2. 通俗版

可以把它理解成几个训练小组共同培养同一个模型。每个小组内部网络快，先各自训练一段时间；小组之间网络慢，就定期交换训练结果。难点是不能把不同版本的结果混在一起，也不能在某个小组掉线后只恢复模型、却忘了优化器和已经读过的数据。这个项目要实现这些协作规则，再通过实验决定多久交流一次既能减少等待，又不会把模型训坏。

## 3. 工程技术版

以已有 FSDP2 和低通信训练方法为基础，实现 CUDA/NCCL 与 Ascend/HCCL 训练组之间的外部同步层。该层负责参数 delta 的分片传输、版本检查、重试去重和完整轮次提交，并将模型、内外部优化器、随机数状态与数据游标一起保存和恢复。用 8B 主实验、14B/32B 扩展测试验证正确性，测量网络传输、设备与 CPU 搬运、同步等待和恢复成本，并对照同步训练的决策准确率、概率质量与到达目标的时间。

## 4. 面试成果版

以下只适用于实际完成后，括号内容应依据实验填写，不应提前当作成果使用。

针对不同硬件和低带宽连接下的分布式训练问题，我负责实现训练组之间的模型更新同步与恢复模块。组内复用已有分片训练，组间采用版本化更新和完整轮次提交，处理了传输中断、重复重试和模型与优化器恢复不一致的问题。我在实际完成的模型规模上做了训练及故障注入实验，以调优后的同步训练为基线，分别报告模型质量、达到质量目标的时间、通信量和恢复代价；最终保留了满足质量要求且改善训练时间的配置。

## 5. 简历一句话版

开发跨 CUDA/Ascend 训练组的模型更新同步与恢复模块，支持版本化分片传输、重试去重及完整训练状态恢复，并在真实大模型后训练任务中验证质量、通信开销和恢复成本。

这句话必须等相应功能完成后才能用于简历；模型规模与量化结果依据真实验证添加。

## 哪些能力已有替代，哪些工作值得做

| 内容 | 已有替代 | 本项目应该承担的工作 |
|---|---|---|
| 大模型参数分片 | FSDP2、DeepSpeed 等 | 复用并验证，不重写整套分片框架 |
| 减少跨组同步频率 | Local SGD、DiLoCo | 复用算法；验证其在决策后训练上的质量 |
| checkpoint 保存 | PyTorch DCP、训练框架 | 复用保存设施；定义组间轮次与完整状态的一致边界 |
| 容错与低通信组件 | torchft、prime-diloco | 先做可用性验证，避免重新实现已经适用的组件 |
| 昇腾训练后端 | TorchNPU、MindSpeed 等 | 补充选定模型/组件实际缺失的训练支持 |
| 模型、优化器、数据进度跨组一致恢复 | 现有框架中可能部分覆盖 | 对照验证后实现具体缺口，以故障实验证明 |

这些工程能力可以有其他实现。项目价值不在“无人能够替代”，而在能指出现有方案在实际环境中的具体缺口，承担该部分实现，并证明收益。

## 一个可以检验核心能力的具体场景

H20 训练组和 NPU 训练组从同一个模型版本开始，各自完成本轮约定的训练。同步时，NPU 组的一个更新分片已经发送，但后续连接中断；与此同时，H20 组正在准备下一轮。

系统需要确定：

1. 当前轮次是否已完整提交，H20 是否允许开始下一轮。
2. 重传的分片能否被识别，防止同一份更新被累计两次。
3. 恢复后的模型版本是否匹配优化器、随机数和数据游标。
4. 未提交的工作如何重放，已提交的训练进度如何避免重复计入。

第一版要求恢复所有参与组到上一个完整轮次，允许重放未提交工作。之后若支持部分组继续运行，就要显式定义成员版本、聚合权重与重新加入规则；不能默认它与原先同步算法数值等价。

这是值得用代码和实验交付的核心模块。增加几个训练参数或成功跑通一次训练不能证明它已经解决。

## 开始前的判断标准

先用 torchft/prime-diloco 与选定 TorchNPU 环境验证上述场景。如果现有实现直接满足需求，项目应改为明确的上游修复、NPU 支持或真实热点优化；不要为了写一个新框架而复制已有能力。

如果存在明确缺口，先把“缺口、失败复现、修改、恢复证据、完整训练收益”做成一个闭环。8B 是主验证任务，14B/32B 是扩展证据，多模态与自适应同步不作为第一版的必需项。
