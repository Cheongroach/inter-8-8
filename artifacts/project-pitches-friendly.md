# 怎样介绍这个项目，而不把计划写成成果

[原文](project-pitches.md)是通信探针阶段的候选项目与面试模板，包含拟实现的恢复功能。这里按截至 2026-10-25 的实际证据整理可用表述。

项目经历了两个独立方向：先评价 H20 / 910B4 的训练系统收益，再迭代 Laya 的决策质量。介绍时应先选择自己承担的方向，避免把 Qwen 训练速度和 Laya 判断能力混为一个成果。

## 一段可以直接使用的说明

我负责搭建可复核的跨硬件训练对照，先验证不同节点上 H20 与 910B4 的 CPU 中转聚合，再比较混合 4＋4 与同构八卡、生成 / 更新分工和发布频率。预验没有证明混合胜过更快同构，因此没有把“能跑”当成收益。后续 H20 两机 16 卡的三模型、七配置、两次计时显示，27B 在 Socket 下把分片留在机内可将 16 更新耗时从 660.09 秒降到 216.60 秒；低频参数平均改变训练规则，未作同质量加速声明。新版 NPU 与混合两组最终取消，三组强比较仍缺失。

这段体现“负责什么 → 怎样对照 → 观察到了什么 → 怎样做取舍”。没有声称恢复已实现，也没有声称千卡性能或费用收益。

## 决策质量方向的说明

我建立了固定版本、数据隔离与验证选优的 Laya 质量实验，保留第一轮校准负结果，并用独立新保留集验证第二轮新闻分类 NLL 改善。第三轮使用 Banking77 9,229 条训练标签拟合词法和冻结 Encoder 分类头；验证选择的概率融合在 3,072 条测试上为 91.67%，比词法基线 90.82% 净多答对 26 条，配对区间支持本次准确率改善。概率指标退化也完整披露，保存分类头、逐样本概率与 ID 映射，16 例公共 API 回放选择一致。

这是监督固定 schema 适配，没有更新原 Encoder / typed head；不能描述为新基础模型或 SOTA。Jev 缺真实 API 调用证据，不列模型对战成果。

## 原拟实现的恢复价值仍在哪里

传输中断时必须识别完整提交、避免重复聚合，并恢复模型、优化器、随机数状态与数据进度；这是具体可检验问题。但 torchft、prime-diloco、PyTorch checkpoint 已有相关设施，必须先找真实缺口，再实现和故障验证，不能仅凭模块命名主张原创。

如果以后推进，应形成“缺口 → 失败复现 → 修改 → 恢复证据 → 质量与时间”的闭环。当前原模板中的恢复一句话不得当成已完成成果使用。
